# Idioma (español)

Este despliegue es **solo en español**. El idioma de la interfaz no depende del
navegador: si no hay nada elegido, arranca en español.

## Qué hace cada desarrollador

Nada. Al clonar y levantar el proyecto la interfaz sale en español.

Si alguien necesita inglés por un rato (por ejemplo para comparar contra
upstream), lo elige en **menú de usuario → Idioma → English**. La elección se
guarda por navegador en `localStorage["i18nextLng"]` y no afecta a los demás.

Para volver a español: el mismo selector, o entrar con `?lng=es`.

## Por qué sale en español

`src/i18n.ts` inicializa i18next así:

```ts
fallbackLng: "es",
detection: {
  order: ["querystring", "localStorage", "cookie"],
  caches: ["localStorage"],
},
```

`navigator` **no** está en el orden de detección a propósito: antes un navegador
en inglés hacía que toda la aplicación saliera en inglés.

Orden real de decisión:

1. `?lng=es` en la URL
2. lo que la persona haya elegido antes (`localStorage`)
3. cookie
4. si nada de eso existe → `fallbackLng` = español

## Lo que sí hay que hacer por entorno (backend)

El código y las traducciones están en el repositorio, pero **el catálogo de
diagnósticos y los valuesets viven en la base de datos**. Sin estos comandos la
interfaz está en español pero el buscador de diagnósticos aparece vacío:

```bash
python manage.py migrate
python manage.py load_icd10                    # 14.484 códigos CIE-10
python manage.py sync_valueset --overwrite True
python manage.py load_fixtures                 # datos base, incluidos cuestionarios
```

`load_fixtures` ejecuta un script (`care/fixtures/scripts/default_fixtures.py` por
defecto) y desde ahí se leen los cuestionarios traducidos de
`data/questionnaire_fixtures.json`. **No corre en producción** (`IS_PRODUCTION`
lo bloquea), así que en un entorno productivo esos cuestionarios hay que cargarlos
con el script que corresponda.

Si el entorno ya existía antes de la migración a CIE-10, `load_icd10` y
`sync_valueset` son los dos que suelen faltar.

## Backend: `LANGUAGE_CODE`

`config/settings/base.py` define:

```python
LANGUAGE_CODE = "en-us"
TIME_ZONE = "America/Caracas"
LANGUAGES = [("en-us", _("English")), ("es", _("Spanish"))]
```

`LANGUAGE_CODE` afecta lo que Django traduce del lado servidor y lo que devuelve
`get_language()`, que es lo que se usa para pedirle a SNOMED el
`display_language`. La interfaz **no** depende de este valor. Cambiarlo a `"es"`
es opcional y no rompe nada.

## Archivos de traducción

| Archivo | Uso |
| --- | --- |
| `public/locale/es.json` | Interfaz en español (6.926 claves) |
| `public/locale/en.json` | Interfaz en inglés (mismas claves) |

Los dos archivos tienen que tener **las mismas claves**. Para verificar:

```bash
python3 -c "
import json
en=json.load(open('public/locale/en.json')); es=json.load(open('public/locale/es.json'))
print('faltan en es:', len(set(en)-set(es)), '| faltan en en:', len(set(es)-set(en)))"
```

Los textos de los cuestionarios no están ahí: viven en
`data/questionnaire_fixtures.json` (backend) y se cargan desde el fixture
script que ejecuta `load_fixtures`.

## Agregar otro idioma

1. Agregar la entrada en `LANGUAGES` (`src/i18n.ts`).
2. Copiar `public/locale/en.json` a `public/locale/<código>.json` y traducir.
3. Si el idioma necesita formato propio de fechas, agregar su locale en
   `src/Utils/dayjs.ts` (`dayjs.locale`) y en `src/Utils/intl.ts`.

Las fechas siguen el idioma de la interfaz mediante `src/Utils/intl.ts`
(`formatLocalDate`, `formatLocalTime`, `formatLocalDateTime`). No usar
`toLocaleDateString("en-US")` ni `toLocaleString()` sin locale: eso vuelve a
mostrar fechas en inglés aunque la interfaz esté traducida.
